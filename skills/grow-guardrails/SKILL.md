# 関所を育てる

関所は最初に全部入れない。始めに決めるのは少しだけで、あとは痛みが出たときに1つずつ足す。決まりは文章より機械で落とす。文章には「どこで落ちるか」と、機械で確かめられないことだけを書く。持ち主の Web アプリ（network-designer）で固まったやり方。

## 始めるときに決めること

利用者に聞いて、AGENTS.md に1行ずつ書く。わからない項目は空けておき、決まったときに書く。別スレッドで自走していて聞けないときは、自分で決めて「（仮）」を付けて書き、最後の報告にその一覧を載せて確かめてもらう（決まったら「（仮）」を外す）。

1. **正本**：どのデータ・どの入力が正で、どこはそれを表示するだけか。表示する側で正本の項目を編集できるようにしない。
2. **データの形の置き場所**：保存する形を Schema と基準の例文書の1か所で固める。画面より先に固める。画面やAPIごとに独自の形を作らない。
3. **確かめる役**：入力の検証はサーバーだけが行う。画面は結果を表示する。画面から届くもの（本文・クエリ・ヘッダ・ID）は書き換えられる前提で扱う：誰の要求かは認証から決め、点数・合否・金額のように導ける値は受け取らずにサーバーが計算し、正解や他人のデータは画面へ送らない。自分専用などで緩めるときは、そう決めたことを AGENTS.md に1行残す。
4. **LLM に渡さないもの**：顧客データ・実名・秘密など。開発では架空データだけを使う。
5. **後回しにするもの**：AGENTS.md ではなく予定の文書（roadmap）に置く。利用者が話題にするまで提案しない。

API と DB を持つアプリなら、1〜3 を API と DB に当てはめたルールと落とし方を [api-db.md](api-db.md) に置いてある。

最初に入れる道具は2つだけにする。

- **`check` を1本**：整形・静的検査・テスト・型チェックをまとめて流す。前提がなくてスキップされたテストは失敗として扱う（「ok」に見えて実は流れていない、を防ぐ）。
- **約束の一覧**（`docs/guarantees.md`）：「約束 | 確かめるテスト」の表。最初は空でよい。一覧に挙げたテスト名が実在するかを確かめるテストを、一緒に入れる。利用者はテストのコードではなく、この一覧をレビューする。

**Web アプリ（React＋TS）で、雛形 app-template（`~/project/prod/template`）が手元にあるなら、そこから始める.** 雛形は持ち主の非公開のもので（共通部品 sx-ui は公開：https://github.com/lenalab-me/sx-ui）、雛形が無い環境ではこの段落を飛ばし、上の「最初は2つだけ」から始める。 check と約束の一覧のほかに、共通部品（`@sx/ui`。`~/project/prod/sx-ui`）のロック、画面ファイルの書き方の検査、e2e（全ルートの基準画像・コントラスト・a11y・フォーカス）が最初から入っている。どれも network-designer で痛みを払って入れた関所なので、「最初は2つだけ」の例外として最初から入れてよい。画面の書き方の検査は部品を使う約束と組なので外さない。e2e の一式は、画面が少ない小さなツールで重ければ、利用者に聞いて痛みが出るまで外してよい。始め方は雛形の README、部品が足りないときは sx-ui で足して版を上げる（アプリに写さない）。

## 作業中のループ

[triggers.md](triggers.md) のサインが出たら、対応する関所を利用者に提案する。同じ指摘を2回したら、それもサインとして扱う。入れるときは次の順に進める。

1. 規則・計算・形を1か所に寄せる（関数1つ、表1つ、Schema 1つ）。
2. 使い忘れたり、2か所目に書いたりしたら落ちるテストか検査を足す。できれば型やコンパイルで落とす。次に強いのは check、最後が起動時の検査。
3. 約束の一覧に1行足す。
4. その部分のコードをわざと壊し、落ちることと、そのときの文言をコミットの本文に書く。戻してから通ることも確かめる。壊れても気づきにくい約束（保存の形、再送・競合、権限、生成の結果）は、壊し方を自分で選ばず、別のモデルの壊し役に攻めさせる（[breaker.md](breaker.md)）。
5. AGENTS.md には「〜を使う（使い忘れると〜が落ちる）」の1行だけを書く。

## 足しすぎを戻すサイン

- 検査が構文解析や作り込んだ仕組みを始めた → 行単位の素直な照合に戻す。片方向で足りるなら片方向にする。
- 実装をなぞるだけで必ず通るテストや、テストの本数を成果にしている → 消す。テストは、壊れても気づきにくい境界に絞る（保存の形、再送・競合、生成の結果）。
- AGENTS.md に、時期で変わる優先順位や日付が溜まった → 予定の文書へ移す。AGENTS.md は毎回守るルールだけにする。
- 途中で基本設計・詳細設計を書こうとしている → 書かない。最後にコードから起こす。決めた理由だけは計画書（`docs/decisions/`、書いたあとは書き換えない）に残す。
- 疎結合のために、規則を分けて別々の場所に写している → 1か所に寄せ、機械に突き合わせさせる。
- 壊し役の穴を塞ぐたびに、また次の穴を探している（重箱の隅のループ） → 1往復で止める。起こりそうにない壊し方は受け入れ、塞ぐのに仕組みが要るものは塞がない。

## 区切りでの振り返り

機能の区切りで、git log・記憶・会話から「2回以上した指摘」「利用者が画面で踏んだ不具合」を数える。関所にできるものは提案する。できないもの（何を作るかの判断、push の確認など）だけを文章に残す。

- 区切りの流れは `agentlog timeline --repo . --since 前の区切り` で、利用者の発言とコミットを時刻順に見る。
- 会話は `agentlog search 'REGEX' --who user --project NAME` で探し、`agentlog show ID --at TIME` で前後を読む。消えたログは（写しがあれば）`--root ~/.local/share/agent-log-archive/claude/projects` で写しを探す。
- 同じ失敗のくり返しは `agentlog repeats --project NAME` で数える。効いたかどうかは、関所を入れた時刻で2回に分けて流し（`--since 前の区切り --until 時刻` と `--since 時刻`）、前後を比べる。道具ごとの `agentlog tool`、日ごとの `agentlog daily` も同じように使える。
- 待ちや、毎回その場で組み立てているコマンドを減らすときは、[speedups.md](speedups.md) の 4 段（見つける・数字で確かめる・道具にする・効いたかを見る）で進める。
